# Project guidance

Movies is an Android Kotlin/Compose application with title search and paging, persisted favorites, snapshot-based movie details, and native/interstitial advertising. Read [architecture](docs/architecture.md), [verification](docs/verification.md), and the [advertising SDK guide](docs/ads-review.md) for current behavior.

- Use readable, idiomatic Kotlin, constructor injection with Hilt, and existing project conventions.
- Implement the requested scope. Avoid unnecessary abstractions, dependencies, screens, and functionality. Ask before expanding scope or changing business rules.
- Prefer stable dependencies and APIs. Explain and obtain approval before adding experimental APIs, preview dependencies, or experimental build settings.
- Group functionality under its owning feature. Search, Favorites, and Details each have `domain` and `impl` modules. Domain exposes required models, contracts, mapping functions, and navigation keys; implementation owns presentation, use-case/repository implementations, Retrofit APIs/DTOs, and Room code. Keep implementation classes internal except entry points needed by application composition.
- Keep `core:domain` plain Kotlin. It owns shared movie models, common failures, and Result-based base use cases. Keep DTOs out of UI state. Core must not depend on features or app. Features consume other features through their domain modules.
- The app owns Navigation 3 back-stack handling and destination composition. Use MovieNavigator for mutations. One saveable back stack has entry-scoped ViewModels; selecting Search pops Favorites. Details carries a serializable snapshot, supplied to its ViewModel through Hilt assisted injection. Do not add navigation serialization to Movie.
- ViewModels own screen state and message/action behavior. SearchViewModel exposes a cached composite PagingData flow, combines source ad anchors with available native ads, and updates screen status and pagination feedback in its StateFlow as page requests start and complete. SearchRoute collects the feed and screen state without sending Paging state back to the ViewModel. Screens render supplied rows without ad eligibility or insertion logic. SearchViewModel resolves status messages through ResourceProvider; its core:ui implementation uses ApplicationContext. Keep Context and Resources out of ViewModels. Static UI labels remain string resources resolved in UI.
- Inject ObserveFavoritesUseCase and UpdateFavoriteUseCase directly into feature ViewModels. Search and Favorites track observed/pending ID sets; Details owns its movie and uses one nullable favorite flag and one saving flag. Database observation confirms writes. MessageScaffold handles messages, dismissal, and retrying a failed write by message identity.
- Interpret HTTP and OMDb response status at the repository boundary. Local catalog failures are InvalidQuery, InvalidPage, and MissingApiKey. All failed OMDb bodies inside successful HTTP responses use one Backend exception preserving Error text, including movie-not-found. Do not classify backend message strings. CommonException covers transport, HTTP, invalid data, and storage failures. Give error types KDoc; create a fresh Throwable for each occurrence.
- Preserve coroutine cancellation. Base use cases return expected operation failures as Results, log unexpected Exceptions, and propagate JVM errors. Avoid redundant dispatcher switches around Retrofit suspend calls and Room operations.
- Ads belong to `sdk` (contracts/session ownership/display eligibility), `sdk:admob` (the only module importing Google ads classes), and `sdk:launch` (launch eligibility and DataStore history). Features depend on sdk; app also includes implementation modules and supplies IDs. Bind implementations in their owning modules.
- Preserve ads rules: request native slots once when SearchViewModel starts; show native ads only when the current list contains at least three movies (excluding ad rows); anchor the two native slots after the first and second movies; omit unfilled slots. Keep resources for the ViewModel lifetime. Interstitial eligibility starts on the second recorded cold launch and continues across later launches until SDK-confirmed presentation is persisted. Offer only an already-prepared ad at the existing Details transition, without waiting for loading. Do not add request retries, refresh timers, formats, placements, or frequency changes without approval.
- Keep initialization process-owned and off Main. Marshal SDK callbacks that change session/UI state to Main. Destroy unused/late native ads and released fullscreen resources. After fullscreen handoff, caller cancellation stops waiting; SDK terminal callbacks still release ownership and complete presentation accounting.
- Keep user-visible local text in string resources; backend text may be displayed with a resource fallback. Give runtime protocol/configuration/timing values named constants.
- Support system font sizes with wrapping and growing/scrollable layouts. SearchScreen has one preview function per main state: prompt, loading, error, empty, results. Use @PreviewScreen for each to cover default and large fonts. Do not add Search component, ad-variant, or duplicate theme previews. Other requested UI previews use supplied state/callbacks without ViewModels or network access.
- Keep credentials and machine-specific settings in ignored local configuration. Use the public Google sample ad IDs until real IDs are configured outside committed source. Do not commit secrets, caches, or build output.
- Keep existing Markdown documentation accurate when architecture, setup, or behavior changes.
- Keep each logical change in a separate, buildable commit: `Scope: imperative description`. Preserve unrelated local changes. Do not push or change external resources without explicit authorization.
